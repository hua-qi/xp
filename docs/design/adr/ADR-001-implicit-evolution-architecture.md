# ADR-001: 极简入参、异步抽取与显式反馈架构重构

**状态**: 已采纳
**日期**: 2026-04-03

## 背景

当前系统包含 `search_best_practices` 和 `finalize_task` 等核心工具，在实际演化与推断中面临以下痛点：
1. **大模型认知负担重**：`finalize_task` 需要大模型填写的字段极多（多达 8 个，包括 `task_description`、`solution_summary`、`key_decisions`、`final_response` 等），不仅消耗 Token，还容易因格式问题导致调用失败或降低调用意愿。
2. **自动推断极易误判**：目前推断采纳情况底层依赖 `final_response` 与历史经验的“向量余弦相似度”。这种做法无法区分“采纳了该经验”与“探讨了该经验但发现没用甚至踩坑”，导致无用经验依然享有高相似度评分，劣质经验无法被淘汰。
3. **同步阻塞体验差**：`finalize_task` 需要等待结构化抽取、Session 落盘、向量推断全部完成后才返回结果给大模型，严重阻断了 Agent 的快速收尾工作流。
4. **逻辑断层**：原有执行逻辑在 `InferAdoptionCommand` 中使用了本次新提取经验的 ID 进行采纳推断，而非实际需要验证的搜索到的历史经验 ID。

## 决策

我们决定重构工具入参和后台执行流，采用**“端侧极简、后台异步抽取与显式反馈”**的全新架构。

### 2.1 端侧工具极致精简
- **`search_best_practices`**：维持现状，保留现有的 `query`, `tags`, `top_k`, `session_id` 字段，确保检索参数的灵活性。
- **`finalize_task`**：全面重构，抛弃繁重的结构化参数。仅保留：
  - `session_id`（选填，关联上下文。如果全新任务未检索，允许为空）
  - `task_description`（必填，一句话说明本次任务是什么，防止后台抽取上下文断层）
  - `learnings`（必填，大模型自由发挥的文本总结，讲清学到了什么/有什么坑）
  - `adopted_experience_ids`（选填，大模型明确声明采纳了的历史经验 ID 数组）
  - `rejected_experience_ids`（选填，大模型明确声明无效或坑人的历史经验 ID 数组）

### 2.2 异步极速响应 (Fire and Forget)
MCP Tool 层接收到 `finalize_task` 请求后，立即向 Agent 返回 `{"status": "ok", "message": "经验已提交"}`，解放 Agent 工作流。实际的解析、推断与落库全部打包压入后台异步事件队列（Async Tasks）。

### 2.3 后台异步“智能拆解” (Async Extraction)
在后台异步进程中，利用内置的轻量级 LLM 将大模型传入的自由文本 `learnings` 智能拆解映射到核心域模型上。将其提取为标准的 `task_description`、`solution_summary`、`key_decisions` 和 `tags`，生成新的经验存入持久层。
**上下文拼接增强**：如果存在 `session_id`，后台提取器会先去数据库反查当初 Agent 的 Search `query`，将其与 `learnings` 拼接后一并交给轻量 LLM 进行抽取，弥补单句 learnings 的上下文断层。

### 2.4 废除相似度推断，回归大模型显式声明
彻底废除原本不可靠的向量相似度 `InferAdoptionCommand`。改为信任且仅信任大模型的显式反馈：后端 Feedback Engine 依据传入的 `adopted/rejected_experience_ids` 数组，直接精准调整对应历史经验的置信度 (confidence)。

### 2.5 强健的异常容错与兜底机制
核心链路后置为异步处理后，必须建立极强的容错能力：
- **提取失败兜底降级与回收**：若后台 LLM 拆解任务超时或输出非法的 JSON 格式，坚决不丢弃数据。系统将原汁原味的 `learnings` 整体存入 `solution_summary` 字段中，并将该经验状态标记为 `DRAFT` 或 `NEEDS_REVIEW`。后台会引入定时清理与二次重试聚合进程，若多次重试（如 3 次）仍失败，则彻底归档或删除，避免脏数据堆积。
- **无效幻觉 ID 静默过滤**：针对大模型可能幻觉出的不存在的经验 ID，Feedback Engine 在更新权重前严格执行 `store.get()` 的有效性校验，遭遇幻觉 ID 静默丢弃并记录 Warn 日志，绝不中断正常的数据闭环。

## 备选方案
在推断经验是否被采纳的环节，我们考虑过以下备选方案：
1. **维持现状（向量相似度推断）**：基于大模型的 final_response 与历史经验的余弦相似度推断。因无法有效区分“采纳成功”与“尝试后失败”的场景，导致数据质量下降，被废弃。
2. **后端 LLM 语义判断**：将会话历史发给后端的 LLM 进行推理。虽然准确率较高，但增加了后端链路的调用复杂度和耗时，且有时难以揣摩端侧 Agent 的真实意图，故未被采纳。

## 结果

### 正面影响
- **极大地降低 Agent 门槛**：输入字段大幅缩减，自由文本 + 明确 ID 的组合极大提升了大模型调用工具的成功率和顺畅感。
- **精准的反馈飞轮**：由大模型在上下文中显式声明“有用/坑人”，解决了向量相似度的结构性误判问题，使知识库的新陈代谢变得绝对可靠。
- **丝滑的工具体验**：同步变异步，Agent 提交后即刻完成所有工作流程，彻底消除了调用堵塞感。

### 负面/妥协 (Risks)
- **异步排查难度增加**：数据落库、LLM 抽取错误等逻辑变为了后台静默发生，对后台的日志监控和状态字段（如 DRAFT）依赖提升。
- **Agent 上下文追踪负担**：大模型需要在多次对话的上下文中记住并提取检索步骤获得的正确经验 ID 提供给 Feedback 数组，可能仍有一定的 ID 遗漏概率。
